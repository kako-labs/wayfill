# Provider boundary and live-data status

## What is implemented

Android `dev.fuelpilot.data.poi.gateway.GatewayStationDiscovery` implements `StationDiscovery`. It POSTs bounded JSON to the HTTPS origin supplied in `GatewayConfig`; `null` configuration returns `UNCONFIGURED` without networking. The config has no provider key. The default transport disables redirects, sets four-second connect/read timeouts and a five-second coroutine deadline, caps responses at 256 KiB, and never logs URLs, request locations, provider messages or credentials. External coroutine cancellation propagates. Typed catalogs carry provider identity, native coordinate system, fetch/expiry times, cache provenance and an explicit false road-metrics flag.

`server/gateway.py` is a Python-standard-library service and real Opinet adapter. Run from the repository root with `server/run.sh <env file>` (or `python -m server.gateway` with the environment set); deployment is described in [gateway-deploy.md](gateway-deploy.md). It binds `WAYFILL_HOST:WAYFILL_PORT` (default `127.0.0.1:8787`); a TLS reverse proxy (the Cloudflare tunnel) publishes `/v1/stations/discover`, `/v1/stations/route` and `GET /v1/health`. Only the server reads the keys: `OPINET_API_KEY` and/or `OPINET_API_KEY_1`…`_99` (several keys each keep their own 300/day quota and are used in order; one corridor build runs all its searches on one key) and `KAKAO_REST_API_KEY`. Configure them through the deployment environment file, never an Android resource, BuildConfig field, URL, source file, log or committed `.env` file. `WAYFILL_DATA_DIR` holds the persistent quota SQLite files (`opinet-quota-<slot>.sqlite`, named by the variable's number, never the key; `routing-quota.sqlite`) outside source delivery. Startup without a key is allowed and requests report `PROVIDER_UNCONFIGURED` / `ROUTING_UNCONFIGURED`. Per client (the `CF-Connecting-IP` address when `WAYFILL_TRUST_PROXY=true`, which is safe only on loopback behind the tunnel): at most 1,800 requests, 120 uncached Opinet fetches and 30 corridor builds per hour, otherwise HTTP 429 `RATE_LIMITED`; a vehicle refreshing every 5 s with a reused corridor stays far below.

Deployment remains external work. Configure TLS, request/body/time limits and caller rate limits at the reverse proxy before exposing it publicly: the service has a shared provider quota, not per-user authentication. Run one instance or have all instances use the same supported SQLite database volume. Do not split the quota among independent files or delete/reset the quota file on restart. Keep provider credentials/location request bodies out of proxy logs and backups. No backend has been deployed or live-credential call made in this work.

## Official contract verified on 2026-11-11

The [official radius-search specification](https://www.opinet.co.kr/user/custapi/openApiInfoDtl.do?apiId=3) specifies `https://www.opinet.co.kr/api/aroundAll.do`, `certkey`, `out`, `x`, `y`, `radius`, `prodcd` and `sort`. `x` and `y` and the returned `GIS_X_COOR`/`GIS_Y_COOR` are **KATEC**, not longitude/latitude. Maximum radius is 5,000 metres. The adapter uses XML and distance sort (`sort=2`), and supports the five officially listed product codes. It parses only named source fields; it does not infer road distance from the provider's distance field. The source example is documentation, not evidence of a successful live query.

**Live check (2026-11-13, real key):** the service did not follow the page above for the key parameter. With `certkey` both `aroundAll.do` and `avgAllPrice.do` returned HTTP 200 with an empty `<RESULT>`; with `code` they returned rows (55 stations for the documented example point at radius 5,000 m, B027). The adapter therefore sends `code`. The live rows label the brand `POLL_DIV_CO` (the page says `POLL_DIV_CD`); the adapter does not read that field.

The [official access page](https://www.opinet.co.kr/user/custapi/custApiInfo.do) requires a key and gives the general daily limit as 300 calls. The adapter reserves an attempt before calling, including provider failures; SQLite transactions persist a global count through process restarts. It resets at the Korean calendar date and rejects a backward date change. It never automatically retries or follows a redirect carrying the key. The provider timeout is four seconds, with a 256 KiB response cap and at most 200 rows. Exact-query cache entries expire after five minutes, with at most 128 entries; cache hits consume no provider call. Expired cache data is never returned as available or used as failure fallback.

The official nearby response does not contain a price observation timestamp. `priceObservedAtEpochSeconds` therefore stays null: fetch time is not a claim about when a station price changed. Malformed/missing coordinates, nonfinite/invalid prices, duplicate station IDs, provider error schemas, ambiguous empty `RESULT`, oversized responses, missing credentials and exhausted quota all fail closed. No fabricated coordinates, price timestamps, stations or route-safe candidates are substituted.

## Gateway schema v1

`POST /v1/stations/discover`, content type `application/json`, body at most 2 KiB:

```json
{"coordinateSystem":"KATEC","x":314681.8,"y":544837.0,"radiusMeters":5000,"fuel":"B027"}
```

These coordinate values are the official documentation example, not a production default. KATEC x/y use conservative finite numeric guardrails 0..2,000,000; these bounds do not assert a CRS definition. WGS84 x/y mean longitude/latitude and have geographic bounds; they currently produce `COORDINATE_TRANSFORM_UNVERIFIED`. Unknown/duplicate fields and invalid bounds/types are rejected before quota or networking.

A successful envelope includes `schemaVersion:1`, `status:"available"`, `fetchedAtEpochSeconds`, `expiresAtEpochSeconds`, `provenance`, and `stations`. Each row has `id`, `name`, `fuel`, `priceKrwPerLiter`, `coordinates:{system:"KATEC",x,y}`, `providerDistanceMeters`, and `priceObservedAtEpochSeconds:null`. Provenance is `{provider:"OPINET",endpoint:"aroundAll",coordinateSystem:"KATEC",roadMetricsVerified:false,cacheHit:boolean}`. Source rows never implement/extend `FuelStationCandidate`.

Failures are `{schemaVersion:1,status:"unavailable",reason:"..."}` with HTTP 400 for invalid input, 429 for quota exhaustion, or 503 for provider/config/transform failure. Android exposes bounded typed failures rather than raw server text. Server times are restamped to the device clock at receipt (vehicle and gateway clocks differ; the PLEOS emulator ran 0.8 s behind its host): the local fetch time is the receipt time and the remaining lifetime is the server lifetime minus any visible age, never more; a fetch time more than 5 s in the future is invalid. It rejects expired/overlong freshness windows, invalid schema/provenance/coordinates and unverified road claims. It keeps no stale fallback cache.

## Route corridor: `POST /v1/stations/route` (2026-11-13)

`server/corridor.py` serves stations along the active route. Only the server reads `KAKAO_REST_API_KEY` (Kakao Mobility directions, header `Authorization: KakaoAK …`); without it the endpoint reports `ROUTING_UNCONFIGURED`. Body (at most 2 KiB):

```json
{"origin":{"latitude":37.3947,"longitude":127.1112},"destination":{"latitude":37.4979,"longitude":127.0276},"fuel":"B027"}
```

Both points must be inside 32.5–39N / 124–132E. An optional `corridorToken` (22 URL-safe characters) is the private handle the server returned for this trip; see below. An optional `navigationRemainingMeters` is the vehicle navigation's own remaining distance. The server routes origin → destination once (geometry and per-road durations) with Kakao's `RECOMMEND` priority; when that disagrees with `navigationRemainingMeters` by more than max(2 km, 15 %) it also tries `DISTANCE` and keeps the closer one (reported as `provenance.routingPriority`; via-station routes use the same priority). On the PLEOS emulator, Pangyo → Suwon station, `RECOMMEND` took 30.8 km via Uiwang while the navigation guided 23.7 km via the Yongin–Seoul expressway; `DISTANCE` gave 23.2 km on the same main roads. A corridor built without that distance is rebuilt once a request carrying it disagrees. Then then searches Opinet (`aroundAll`, radius 5 km) at centres every 6 km along the route, snapped to a 1 km KATEC grid so nearby corridors share the 5-minute sample cache. **Coverage is proven, not assumed:** every route point (checked every 200 m) must lie within 3.9 km of a search centre, so every station within the 1 km corridor width was inside some search; extra centres are added where bends need them, and routes needing more than 40 searches fail as `ROUTE_TOO_LONG` (about 240 km). Each search costs one unit of the shared persistent Opinet quota. An empty `<RESULT/>` counts as "no stations" only when at least one other search in the same corridor returned rows; all-empty fails closed as `PROVIDER_SCHEMA_INVALID`.

Stations within 1 km of the route are bucketed into ten equal stretches; the one closest to the route in each stretch is measured with a routed origin → station → destination request (detour = via-route minus base route, distance and time). Per station the response gives `alongRouteMeters` (route progress from the current origin), `roadDistanceMeters` (progress plus half the routed detour distance), `etaSeconds` (routed time to that progress plus half the detour time) and `detourSeconds`. Straight-line or provider distance is never used. Every build returns a fresh unguessable `corridorToken`; the corridor is reused for 10 minutes only by a request that carries that token, for the same destination and fuel, while its origin stays within 300 m of the route. Without the token every request is a fresh build, so one caller can neither reuse nor probe (by timing) another caller's trip; only the public per-cell provider samples are shared. Each request re-projects the current origin, so only stations still ahead are returned.

Quotas are reserved before any provider call, all or nothing: the uncached Opinet searches of a build at once (a build may never take the last 60 of the 300 daily Opinet calls, which stay for `/discover`), and Kakao requests in a separate persistent daily quota (`routing-quota.sqlite`, `WAYFILL_ROUTING_DAILY_LIMIT`, default 1000): one or two for the base route, then one per measured station. Exhaustion is HTTP 429 `QUOTA_EXHAUSTED` / `ROUTING_QUOTA_EXHAUSTED`. The gateway has no client authentication (the app holds no credential); the per-client limits above bound what one caller can spend. A snapshot expires after 30 s; `stationsObservedAtEpochSeconds` is the oldest provider search used.

Envelope: `schemaVersion:1`, `status`, `fetchedAtEpochSeconds`, `expiresAtEpochSeconds`, `stationsObservedAtEpochSeconds`, `route:{remainingDistanceMeters,remainingDurationSeconds}`, `coverage:{verified,sampleSpacingMeters,searchRadiusMeters}`, `provenance:{stationProvider:"OPINET",stationEndpoint:"aroundAll",routingProvider:"KAKAO_MOBILITY",coordinateSystem:"WGS84"}`, `corridorToken`, `stations[]` with `id,name,fuel,priceKrwPerLiter,latitude,longitude,alongRouteMeters,roadDistanceMeters,etaSeconds,detourSeconds`. Failures use the same envelope as discover (400 / 429 `QUOTA_EXHAUSTED`, `ROUTING_QUOTA_EXHAUSTED` / 503 `ROUTING_UNCONFIGURED`, `PROVIDER_UNCONFIGURED`, `ROUTE_NOT_FOUND`, `ROUTE_TOO_LONG`, `ROUTING_UNAVAILABLE`, `ROUTING_SCHEMA_INVALID`, `PROVIDER_*`).

Live check 2026-11-13, Pangyo station → Gangnam station (16.8 km): 1.1 s, 4 Opinet searches, 8 Kakao requests, 7 stations; an opposite-direction expressway rest-area station came back honestly with an 809 s detour.

PLEOS end-to-end 2026-11-13 (emulator, live guidance to Suwon station, both keys, gateway via `adb reverse`): the app read the active route (23.0 km), the corridor matched it (23.2 km, `DISTANCE`), five stations came back with routed metrics and `VERIFIED_ROAD_METRICS_WGS84` targets, and the decision engine (range 60 km, reserve 50 km) chose LAST_SAFE_STOP at 4.3 km with a 6-minute detour. A repeated read reused the corridor by token with no provider calls; each read took about 2 s, mostly the four navigation reads of the context checks.

App side: `GatewayRouteCorridor` (data/poi) posts to `<gateway origin>/v1/stations/route`, sends back the last issued token only for the same destination and fuel, and revalidates freshness (≤ 30 s), provenance, fuel, ranges and observation age (≤ 15 min). With an active route, `ProductionStationRepository` uses the corridor instead of the nearby catalog: it needs the navigation's destination coordinates (`ActiveRoute.destinationLatitude/Longitude`, from NaviHelper), requires `coverage.verified`, and accepts the routed path for the navigation's own route only while their remaining distances agree within max(2 km, 15 %) — otherwise `ROUTE_COVERAGE_UNVERIFIED`. Stations beyond the navigation's remaining distance are dropped; the usual context re-check applies. Candidates carry `VERIFIED_ROAD_METRICS_WGS84` navigation targets.

## Exact remaining integration boundary

1. A user-authorized Opinet key and permitted server deployment are required for live testing. None was supplied or searched for; no external API call was attempted.
2. ~~A primary-source verified KATEC definition is required.~~ **Resolved empirically on 2026-11-13** (no primary source exists; KATEC has no EPSG code). `KatecProjection` uses Bessel 1841 TM (38N 128E, k0 0.9999, FE 400000, FN 600000) with the 7-parameter shift -115.80, 474.99, 674.11 m / 1.16, -2.31, -1.63″ / 6.43 ppm (position vector). Evidence: the 55 live `aroundAll` rows for the documented example point, converted with this definition, sat a median 10.6 m from the nearest OpenStreetMap `amenity=fuel` feature and 6.5 m from same-brand features (n=23, all same-station matches within 33 m). The same definition without the datum shift was about 350 m off, and a 3-parameter shift was slightly worse (median 10.0 m). The remaining distant rows had a differently named nearest OSM feature, i.e. the station is missing in OSM. The Kotlin code matches PROJ 9.8 within 5 mm forward and 1 mm inverse across 33–38.7N, 124.5–131E. `ValidatedKatecTransform` converts only inside 32.5–39N / 124–132E and returns null elsewhere. Re-run the comparison if Opinet changes its coordinate output.
3. A navigation SDK adapter must compute actual road reachability/detour/along-route metrics using verified station coordinates. The app now has a production join boundary described below; its SDK ports intentionally remain unavailable until implemented. Provider distance must never populate road-distance/route-progress fields. Native-KATEC data cannot be silently relabelled WGS84.
4. The nearby source has no observation timestamp; price-age policy must explicitly handle that unknown. Do not replace null with fetch time to claim fresh price observations.

Verification: `python -m unittest discover -s server/tests -v` (gateway and corridor, with fake Kakao/Opinet fetchers; the corridor tests also check the coverage proof on random winding routes and the KATEC vectors) exercises the real XML parser, provider request construction, actual local HTTP handler, schema/coordinate rejection, cache expiry, persistent quota, redaction and unconfigured/unsupported states without external network. Android JVM boundary tests inject transport/decoder to exercise repository validation. Android35 instrumentation also exercises the actual platform `org.json` parser for available/unavailable documents and rejects string booleans/trailing payload. Real TLS/provider deployment remains unprobed without a deployed origin/key. The app build/lint and whole project checks are reported separately by integration.

## App production assembly boundary

`createProductionStations(location, navigation, discovery, roadMetrics, coordinateTransform, fuel)` returns `ProductionStationRepository`, implementing `StationRepository` and `ContextualStationRepository`. The default `fuel` is null: the SDK/host must supply a verified actual vehicle fuel type before any query. No gasoline default is used. The coordinate-transform and road-metrics defaults explicitly provide no capability. Merely configuring an HTTPS gateway or receiving an Opinet catalog cannot produce route-safe candidates.

The coordinator must call `findStationsFor(origin, route)` using the exact fresh location and route supplied to the decision engine. A null route is allowed only after navigation positively reports `RouteResult.Available(null)`. The repository verifies that context before querying and again after navigation computation; a changed route (including route ID/distance), changed origin, stale/unsupported read, or expired snapshot invalidates the result. Standalone `findStations()` also performs these checks using its own context, but does not bind an independently assembled decision input.

`VerifiedStationCoordinateTransform`'s default still returns null; the app wires `ValidatedKatecTransform` (see item 2 above). `StationRoadMetrics` must route the exact raw catalog coordinates through a verified navigation integration and return `VerifiedRoadMetricsSnapshot` echoing the full `RoadMetricsRequest` (origin, route, raw catalog). A snapshot must have a nonfuture measurement time, an unexpired lifetime no longer than 30 seconds, exactly one metric per raw station ID, finite nonnegative road distances, nonnegative ETA/detour, and route progress within the matching route. Active routes require along-route and detour values; confirmed no-route requests require those fields to be null. Explicitly unreachable stations are excluded. Missing, duplicate, extra, stale or invalid metrics fail closed, with no fallback to source distance.

The raw catalog is independently revalidated at this join, including its five-minute maximum freshness window, source provenance, exact fuel, native coordinates, IDs and numeric fields. The join uses navigation road distance for candidates and never reads `providerDistanceMeters` as road distance, detour or reachability. Source price observation time remains null. Opinet's nearby catalog supplies no verified current opening status, so candidates preserve `OpenStatus.UNKNOWN` and `businessInfoFresh=false`; this boundary does not assert that a station is open.

For an active route the SDK adapter must also prove `routeCoverageVerified=true`: the catalog covers the relevant corridor and potential stops up to the reserve boundary, so a last-safe-stop comparison is meaningful. A single current-location 5km nearby query is not that proof. Missing corridor coverage stays `ROUTE_COVERAGE_UNVERIFIED`; implementing route-corridor collection/coverage belongs to the live navigation/provider integration. Fuel reserve and remaining-range calculations use actual station-access road distance including detour; route progress only orders candidates and times the alert.

`readStations()` / `readStationsFor(origin, route)` expose bounded typed failure reasons (including unverified fuel/transform, discovery configuration failure, stale catalog, missing/stale/invalid road metrics and changed context). The `StationRepository` API maps all these failures to `StationResult.Unavailable` with no stale candidate fallback. Coroutine cancellation propagates. JVM tests cover these failure paths and the verified metric join using injected local ports; they do not claim live provider, projection or SDK validation.
