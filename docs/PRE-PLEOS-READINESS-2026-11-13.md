# PLEOS 실행 전 제품 인계 · 2026-11-13

현재 디자인은 사용자가 확정한 **소프트 선셋 + 도로 띠 뽀동이**다. 브랜치는 `feature/prepleos-hardening-20261113`, 앱 버전은 `0.2.0-prepleos`(code 2)다. [팀원 인계](TEAMMATE-PLEOS-HANDOFF-2026-11-13.md), [화면 모음](screen-gallery.html), [직접 조작](../web/companion-preview.html), [새 캐릭터 동작](../web/sunset-motion-review.html)에서 먼저 확인한다.

이 작업은 일반 Android에서 실행 가능한 앱과 실제 연결 경계를 준비하는 범위다. 실제 PLEOS/Devbox/실차가 없으며 공급자 승인·키·SDK 실행 결과를 대신 만들지 않았다. **기기에서 실행만 하면 실데이터 추천까지 된다고 해석하지 않는다.**

## 구현한 제품 흐름

- 정차 홈과 주유 안내는 같은 추천 컴포넌트를 쓴다. 추천 이유 → 주유소·거리·추가 시간 → 바로 안내/나중에 순서다. 긴 이름, 넓은 화면, 420×620 및 640×340 작은 창을 지원한다.
- 주행/Unknown은 홈 메뉴·설정·기록·삭제 창을 숨긴다. 주행은 작은 정지 뽀동이와 필요한 행동만, Unknown/오래된/지원되지 않는 정보는 안내 행동 없이 상태를 표시한다. 주유 후·요청 중·성공·실패는 같은 디자인의 상태 화면을 쓴다.
- 앱이 지도를 그리지 않는다. 내비 요청은 정확한 추천 키·주유소·경로 ID와 결합하며, 실제 SDK 성공 응답 전에는 성공으로 표시하지 않는다. 타임아웃/취소/경유지 한도/오래된 알림 액션은 기존 계약으로 거절한다.
- 주유 확인 직후 과거 추천을 지우고 즉시 에너지·경로를 다시 조회한다. 같은 연속 이벤트 ID는 불필요한 재조회를 반복하지 않는다. 주유 시연도 확인 후 연료 값이 바뀌므로 실제 UI 흐름을 검토할 수 있다.
- 백그라운드 알림은 같은 런타임/추천 정보를 사용한다. 두 행동, 15초 만료, 추천별 15분 쿨다운, 미룬 추천 억제, 숨김 상태의 독립 관찰, 재개 시 오래된 알림 제거를 유지한다. 위치·외형·주행 UX 허용 여부는 PLEOS OS에서 확인해야 한다.
- 확인된 주유 이벤트는 기기 내 기록에 저장한다. 목록/상세/빈 상태/회전 후 복원/삭제 확인이 연결됐다. 없는 주유량·거리·주유소·가격·연비를 만들지 않는다. 시각은 **앱에서 신호를 확인한 시각**이다.
- 기록은 최근 90일/최대 100건이다. 삭제는 주유량·거리 기록을 지우며 중복 억제 정보(최대 90일/256건)는 남긴다. 저장 실패 시 삭제 성공으로 표시하지 않는다. 클라우드 백업과 기기 전송 제외 규칙을 추가했다.
- calm과 별도로 추천·소량·충분한 주유·저연료 회복에 각각 32개의 실제 포즈를 사용한다. 웹과 Android의 8×4 시트 바이트·프레임 시간표가 같다. 화면 시계에 동기화해 15~20개의 포즈를 초당 표시하고, 인접 포즈 사이의 보간은 최대 45ms로 제한한다. optical-flow 왜곡·크로스페이드 겹눈이 있는 자동 중간 프레임은 제품에서 제외했다. 추천 입장 시각을 세션 상태가 소유해 화면 재진입/회전으로 같은 인사가 처음부터 재생되지 않는다.
- 앱 아이콘과 시스템 알림의 큰 아이콘도 새 캐릭터다. 알림 이미지는 다운샘플링한다. 정지 표시에는 프레임 반복 갱신이 없고 기본 깜박임도 대기 구간 동안 잠든다. 새 시트는 리깅된 벡터나 60fps 영상이 아니다.
- `WAYFILL 시연`은 debug 전용 별도 런처/런타임/저장소다. 실제 SDK가 없는 운영 시작은 Unknown/Unsupported로 잠긴다. 시연 진입을 위해 운영의 안전 정책을 풀지 않는다. release에서 시연 코드·런처를 검사한다.

## Motion Care에서 참고하고 달리 설계한 점

2026-11-13 fetch 기준 Motion Care main `2712673`의 홈·화면 모음·검증 기록을 읽었다. 실제 기능만 메뉴에 배치하고, 넓은/좁은 화면을 다르게 구성하며, 실패와 재현 절차를 기록하는 방식을 따른다. WAYFILL에는 운전자 프로필·좌석·운행 점수 대신 주유 타이밍·추천 정체성·도달 가능성·내비 응답·백그라운드 만료가 중요하므로 그 경계를 우선했다. Motion Care의 PLEOS 검증을 이 앱의 검증으로 옮기지 않았다.

## 이 노트북 검증

최종 실행 결과는 아래 검증 절에 기록한다. 환경은 JDK17/Android SDK35/Node22/Python, 일반 AOSP API35 AVD, CPU 소프트웨어 렌더링이다. 전체 앱은 1682×1210/density160, 컴포넌트는 420×620/640×340/1600×1000을 사용한다. Windows 시간대는 Asia/Seoul, AVD는 기본 UTC라 캡처의 기록 시각 표현이 다를 수 있다. 테스트는 건너뜀과 통과를 구분한다. 캡처를 직접 열어 봤으며 디자인·모션은 실제 크기로 사용자가 최종 확인해야 한다.

## 다음 PLEOS 기기에서 연결할 실제 입력

1. `FuelPilotApplication.dependencies`에서 현재 연결한 AAOS/Pleos 어댑터의 SDK·권한·속성·콜백을 확인한다. 실제 정차/UX 제한/에너지/위치/내비 상태를 검증한다. 없는 데이터는 계속 Unsupported/Unavailable이다.
2. `AaosVehicleEvents.refuels`에는 아직 운영 주유 이벤트가 없다. 신뢰할 수 있는 주유 전용 이벤트의 안정 ID를 연결한다. 단순 연료/거리 증가를 주유라고 추측하지 않는다.
3. 실제 연료 종류, 검증된 WGS84→KATEC 변환, 실제 도로 거리·우회 시간·경로 후보 수집 범위를 `createProductionStations`의 포트에 공급한다. Opinet의 반경/직선 거리를 도달 가능성이나 마지막 기회로 쓰지 않는다. 현재 기본 포트는 이를 거절한다. 검증된 WGS84 `NavigationTarget`은 candidate→Assist→WaypointRequest까지 이미 보존되며 좌표 누락·무효·station ID 불일치는 SDK 호출 전에 `Unsupported`다. [공급자 계약](data-provider.md)을 따른다.
4. 공급자 API 승인/서버 키/HTTPS 배포 주소를 준비한다. 키는 서버에만 둔다. 이번에 서버를 배포하거나 실제 키로 호출하지 않았다.
5. `scripts/pleos_probe.py`로 정확한 대상·현재 사용자·권한·차량/내비 서비스를 먼저 관찰한다. `scripts/pleos_e2e.py`의 상태 표와 전제조건을 확인한 뒤 명시한 시나리오만 실행한다. 실제 창 배치, HUN 만료/미루기/오래된 액션, car-service 재시작과 재구독은 별도 기록한다.
6. 시스템 HUN, Gleo, TTS는 각각 실제 호스트 어댑터로 연결한다. TTS는 `RecommendationSpeechPort`, 음성 선택은 `recommendationVoiceCommand`를 사용한다. HUN이 실제로 게시되고 같은 추천을 처음 claim한 경우에만 한 번 말하며, 앱 표시·알림 만료·버튼 선택·서비스 종료 시 중단한다. 실제 오디오 포커스·내비 음성·통화 충돌 정책은 PLEOS에서 검증한다.
